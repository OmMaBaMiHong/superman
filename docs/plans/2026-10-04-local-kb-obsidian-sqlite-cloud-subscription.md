## 0. 一页结论（TL;DR）

**产品定位（2026-10-04 拍板）**：以 DSH 插件为主体，AI 驱动。主线 = **订阅源/新闻（素材）→ AI 改写 → 生成小红书/公众号等文案 → 发布**（改写发布能力沿既有 studio/pipelines 线推进，不在本文展开）。本文档覆盖两条支撑线：**知识库**（本地 Obsidian 记忆 + 云端知识库）与**云端订阅推荐**。对标 WeSight 只吸收功能与工程思想，不引入其商业模式（见 wesight-benchmark 文档）。

产品分三层，各层职责与存储边界如下：

| 层 | 职责 | 存储 | 是否向量化 |
| --- | --- | --- | --- |
| **DSH 插件本地版**（开源主体，个人用户） | 本地知识库：Obsidian vault 索引、检索、问答；订阅阅读 | **SQLite**（FTS5 + sqlite-vec），单文件、无云也完整可用 | 是（本地 sqlite-vec，embedding 可本地可云端） |
| **FeedFuse 云端** | 会员权益、推荐/热点分发、权益校验、云知识库的**客户端接入与体验组装**（B5） | PG（业务库，已有） | 间接（经统一知识库服务） |
| **统一知识库服务**（**Chaos 体系承载**，多产品共享） | 中台的**定向数据源**（用户绑定关系）：用户数据存储 + 知识沉淀；知识图谱（实体/关系）+ 向量 + 全文检索；按「产品 → 用户」双租户隔离，用户解锁自己的数据（§3 附） | **Neo4j 知识内核（图 + 原生向量 + 全文，源自 Skoob）**+ PG 资产登记 + 七牛云对象存储 | 是（Neo4j 原生向量索引，天王引擎已验证） |
| **Chaos 数据中台** | 采集、清洗、榜单、热点、推荐、开放 API、**素材的分析沉淀（灵感池）** | 自有（PG17 + Timescale + pgvector + MinIO） | 自有 |

云端知识库定位为**多产品共享的统一知识库服务，归 Chaos 体系承载**——对中台而言它是「定向数据源」（用户绑定关系），与爬取的「散装数据源」并列（FeedFuse、Skoob 等都是客户端；方案见 §3 附）。
支付与账号体系复用 sub2api，FeedFuse 云端只做权益映射与配额执行，不重造支付。

```

│  会员权益 / 推荐·热点分发 / 权益网关 / 云知识库客户端体验组装          │
│  PG（业务库：用户、栏目、推送记录、配额计数）                          │
└───────────────────────────────┬──────────────────────────────────────┘
                                ↓ 作为客户端经 API 接入
┌─────────────────── Chaos 数据中台（tian-xia-bang）────────────────────┐
│  ① 统一知识库服务【定向数据源：用户绑定关系】                          │
│     ├─ Neo4j 知识内核（图 + 原生向量 + CJK 全文，源自 Skoob）          │
│     ├─ PG 资产登记（版本/权限/计量/结算；无外键·单表查询）             │
│     ├─ 对象存储：七牛云 Kodo（大块内容/原文快照）                      │
│     └─ 双租户 product_id → user_id；用户只解锁自己的数据               │
│  ② 散装数据源管线（现有能力：采集 14 平台 → 清洗 → 实体/观测           │
│     → 榜单/推荐 → 开放 API）                                           │
│  ③ 分析沉淀：素材流 → 灵感池 → 反哺各产品                              │
└───────────────────────────────┬──────────────────────────────────────┘
                                ↕
┌────────────────────── sub2api（生态公共层）───────────────────────────┐
│  统一身份 / 会员订阅 / 支付 / 模型网关（中转站）                       │
└───────────────────────────────────────────────────────────────────────┘

其他产品（Skoob 等）按同一协议接入统一知识库服务；本地版永远可独立运行。
```

存储分工一句话：**业务事实跟 PG 走，知识本体跟 Neo4j 走，大块内容跟七牛云走，检索语义留在 core 层（本地 SQLite 与云端 Neo4j 是同一套 hybrid 范式的两个实现）。**

## 2. 已拍板决策（Decision Log）

| # | 决策 | 依据 |
| --- | --- | --- |
| D1 | 本地版存储 = **SQLite**（FTS5 + sqlite-vec） | 单用户无并发压力；容量上限 ~281TB，个人知识库规模（≤10万 chunks）绰绰有余；单文件分发，符合开源开箱即用 |
| D2 | 知识源首选 **Obsidian vault**（markdown + frontmatter，只读索引起步） | 用户资产在本地、格式开放、`[[wiki链接]]` 天然是知识图谱的边 |
| D3 | **上云是用户的选择（云存储产品语义）**：本地默认离线完整可用；用户可把知识库上传云端，换取多设备记忆同步；平台将素材用于分析/沉淀/共享的范围在用户协议中约定（法务条款，不是产品门槛） | 用户要的是"换台机器记忆还在"——做用户的云存储。开源版的卖点是"无云也完整可用" |
| D4 | 云端职责 = 会员权益 + 推荐/热点分发 + 权益校验 + **云端知识库（B5）**：保管用户上云的知识库，并向 Chaos 供给分析素材 | 保管方与加工方分离，见 §3 附 |
| D5 | 热点/榜单/清洗内容统一来自 **Chaos 开放 API** | 采集与清洗是 Chaos 的定位，本仓库不重复建设 |
| D6 | 身份与支付复用 **sub2api**，云端只做权益映射与配额执行 | Chaos README 明确「sub2api 承担统一身份、订阅、支付与模型网关」 |

## 3. 板块划分与需求明细

### 板块 A：本地版内核（DSH 插件开箱即用）—— 开源主体

| # | 需求 | 说明 | 验收标准 | 依赖 |
| --- | --- | --- | --- | --- |
| A1 | **KnowledgeStore 存储抽象** | 把 `src/core/knowledge/search.ts` 的检索语义（向量+FTS 双路、RRF k=60、无 AI 降级）与 PG 方言解耦；定义 `upsertChunks / searchVector / searchFts / hybridSearch` 接口；现有 PG 实现迁为 `PgStore` | 两个实现通过同一套测试；Next.js 与插件宿主行为不变 | — |
| A2 | **SqliteStore** | better-sqlite3 + FTS5（关键词）+ sqlite-vec（向量，int8 量化）+ 内容表；单 db 文件；WAL 模式 | 10 万 chunks 混合检索 P95 < 200ms；可从零重建索引 | A1, V2 |
| A3 | **Obsidian 源适配器** | 用户在设置页配置 vault 路径 → chokidar 监听增删改 → 解析 markdown/frontmatter → 切块（复用 `chunking.ts`）→ 入索引；`[[wiki链接]]` 抽为图谱边存表；**只读 vault**；同时兼容非 Obsidian 的普通 markdown 文件夹（同一解析器） | 新增/修改笔记 ≤ 数秒内可检索；删笔记同步删除索引；vault 永不被写入 | A2 |
| A4 | **检索与问答** | 复用 `hybridSearch` 语义与 `/s/api/knowledge/search|ask` 路由，走 SqliteStore；**中文分词**：FTS5 用 bigram/trigram 方案起步（jieba 扩展为备选） | 中文问答能召回 vault 内容；无 AI 配置时 FTS-only 可用（对齐现有降级行为） | A2 |
| A5 | **Embedding 配置化** | 维度与模型不再硬编码（现 0041 锁 `vector(1536)`）：云端 API / 本地 Ollama（768/1024 维）/ 无 AI 降级 FTS-only；sqlite-vec 虚拟表按维度建 | 切换 embedding 模型后可一键重建索引 | A2 |

### 附：云端知识库方案草案（2026-10-04 二轮讨论，待与 Chaos 对齐拍板）

**内核选型（2026-10-04 四轮讨论拍板方向）：统一知识库以 Skoob 图谱/资产体系为内核做通用化。Neo4j 是知识内核，不是要被替代的东西。**

看完 Skoob 代码（`work-space/skoob`，docs/graph-assets.md）后的判断：它已经是完整的知识库平台架构，三层各司其职——
**Neo4j = 知识本身**（实体、关系、画像、模板；天王引擎已在 Neo4j 原生向量索引 + CJK 全文索引上跑了 RRF 混合检索 + 本地 rerank，与 FeedFuse 在 PG 里的 hybridSearch 同一范式且更完整）、
**Postgres = 业务事实**（资产登记/版本/审核/计量/配额/结算/API key；硬规则：无外键、单表查询）、
**对象存储 = 大块内容**（资产包/原文/封面；Skoob 本地开发期为 MinIO，中台已统一为**七牛云 Kodo**，S3 兼容接口不变，接入时直接对齐）。
把这个体系从小说领域通用化到多产品，工程量远小于新起一套。

**通用化要补的四件事**：

1. **本体可插拔**（最关键）：Skoob 本体是小说领域（流派/角色/设定/模板）；多产品要支持各领域注册自己的 schema（Superman 素材本体、Skoob 小说本体并列），Neo4j 侧按领域 label/命名空间隔离。
2. **资产 type 扩展**：`book|genre|agent|setting` → 增加 `note|collection|material` 等通用类型；所有权模型（唯一性/多样性资产、fork、先到先得）原样保留。
3. **检索引擎直接复用**：天王 hybrid retrieval（Neo4j vector + fulltext + RRF + rerank；本地 bge-m3 1024 维或 OpenAI 兼容端点）升格为平台检索服务——embedding 维度问题一并解决。
4. **红线机制保留**：不下发原文、manifest 校验剥离原文、审核轨迹——对用户上传素材同样适用（"版权是这门生意的红线"，Skoob 文档原话）。

**职责分工（终版，2026-10-04 五轮讨论拍板：统一知识库服务归 Chaos 体系承载）**：

- **Chaos 数据中台的数据源分两类**（这是中台的完整定位）：
  - **散装数据源**：公开爬取（微博/知乎等平台），无归属关系，进清洗/榜单/推荐管线——Chaos 现有能力；
  - **定向数据源**：用户绑定的数据，即**统一知识库服务**——双租户（product → user）隔离，用户数据存储 + 知识沉淀，按用户解锁自己的数据。
- **统一知识库服务 = Chaos 体系内的一个服务**：内核沿用 Skoob 图谱/资产体系（Neo4j 知识 + PG 资产登记 + MinIO），部署与运维归中台；Chaos 的 docker compose 增加一个 Neo4j 即可（Skoob 有现成配置可抄）。
- **FeedFuse = 客户端之一**：插件经其云端代理接入；本地 SQLite 版照旧（本地优先），上云同步进统一知识库。
- 数据流：`各产品 → Chaos·统一知识库服务（双租户隔离）→ 素材流 → Chaos 清洗/灵感池 → 分析沉淀 → 反哺各产品`。
- **代码边界（重要）**：Skoob 内核是 AGPL-3.0-only——知识库服务保持独立服务、独立仓库，部署在中台基础设施上，**不把 AGPL 代码混进 Chaos 主仓库**（避免 license 传染）；对外提供网络服务按 AGPL 开放该服务源码，与 Skoob 开源运营路线自洽。

**多租户与权限设计要点**（沿用已认可方案，补 Neo4j 侧）：

- 租户模型：`product_id（产品租户） → user_id（终端用户）`双租户键。PG 资产层用行级安全（RLS）+ API 层双重校验；**Neo4j 侧节点/关系带租户属性、查询强制带租户谓词**——Cypher 没有 RLS，必须靠服务层封装，这也是统一知识库必须独立成服务、绝不暴露原生 Neo4j 连接给各产品的原因。
- 对象存储按 `product/user/` 前缀分桶；每用户可彻底删除，删除事件同步 Chaos 清理派生数据。

**License 注记**：Skoob 为 AGPL-3.0-only。统一知识库服务若基于其代码对公网提供服务，按 AGPL 网络条款需向用户提供该服务源码——Skoob 本就按 AGPL 开源运营，路线自洽；各闭源产品接入只走 API，不混代码。

**PG 形态要点（"巨大的知识库"怎么落）**：

- 原文与附件进对象存储（七牛云 Kodo，S3 兼容），PG 只放元数据 + 向量 + 全文列。
- 分区：按 user_id 哈希分区起步，量再大按时间冷热分层（Chaos 镜像自带 TimescaleDB）。
- **同步原文（markdown），不同步向量**：向量在云端按统一模型重建——各端维度/模型不会打架，将来整体升级 embedding 模型只动云端；本地 sqlite-vec 索引独立存在，互不影响。
- embedding 维度必须参数化（0041 的 `vector(1536)` 硬编码在单机无所谓，在多用户云端会变成全局迁移负担）。
- 在线查询永远限定单用户分区；**跨用户全局分析走离线批处理**（对齐 Chaos worker 心跳模式），不做在线全量 KNN。

**大数据技术栈调研结论（2026-10-04）**：

- 结论：**Hadoop/Hive 现不上**。三个理由：① 规模差 2-3 个数量级——10 万用户 × 1 万 chunks ≈ 10 亿行 / ~1TB 量级，PG 分区 + 离线批处理可消化；② Hadoop 集群需要专职运维，与当前单机单实例的形态不匹配；③ Hadoop/HDFS/Hive-on-MapReduce 本身已是被替代的形态——2026 年大数据主流 = 对象存储 + 开放表格式（Iceberg/Paimon/Delta）+ 独立计算引擎（Spark/Trino），存量 Hadoop 集群都在往这个方向迁。
- 但「存储计算分离、原始数据进湖」的**方向**现在就落，成本近零（对象存储已有——七牛云 Kodo）：
  1. 用户素材原文、分析中间产物落对象存储（七牛云 Kodo）；分析层写 **Parquet**（起步用 DuckDB 查——嵌入式、零运维，与本仓库工程风格一致）；
  2. 出现表级 ACID / 时间旅行 / 多引擎共享需求时，再升级 **Iceberg/Paimon** 表格式（届时 Hive metastore 或 REST catalog 才有引入价值——Hive 只以目录服务的形式回来）；
  3. 计算引擎升级路径：DuckDB（现在）→ Spark/Polars（批任务进入小时级）→ Trino/ClickHouse（交互式分析、行为看板、多团队并发）；
  4. 向量侧：单用户分区内 pgvector 千万级无忧（HNSW + halfvec/binary 量化，内存约 7.6GB/百万向量@1536 维，量化可降一个量级）；若未来出现亿级**全局**在线向量检索，迁 Milvus（存算分离、可挂对象存储），不是上 Hadoop。
- 触发重估的信号（满足其一再谈大数据栈）：总量 >5–10TB；单批任务 >1 小时；分析消费者 ≥2 个团队/产品线；全局在线向量检索进入亿级。

## 5. 关键技术结论备忘（2026-10-04 分析，防遗忘）

- **SQLite 容量**：理论上限 ~281TB；实际几十 GB、百万级行无压力。真正的限制是单写者并发——个人用户场景无影响。
- **本地向量检索**：sqlite-vec 为暴力 KNN（无 ANN 索引）+ int8/binary 量化；10 万级 chunks 毫秒级。规模破百万再议 LanceDB。
- **中文分词是检索质量的最大变量**：FTS5 默认 tokenizer 不切中文（需 bigram/trigram 或 jieba）；现有 PG `to_tsvector('simple')` 对中文同样弱。两边都欠账。
- **pgvector 已落地**（`0041_knowledge_embeddings.sql`：`vector(1536)` + ivfflat + tsvector GIN；`hybridSearch` RRF k=60、无 AI 自动降级）。两个改进顺手做：ivfflat → HNSW；维度参数化。
- **Obsidian 生态现成方案**（吸收优先）：Obsidian Local REST API 插件、mcp-obsidian、khoj（本地优先 + 索引 Obsidian 的完整先例，管线可对标）、Smart Connections。
- **`[[wiki链接]]` = 免费的知识图谱边**，M4 图谱视图的数据源现成。
