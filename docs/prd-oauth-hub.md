## 0. 设计取向（基于开源调研结论）

调研 GitHub 上主流 OAuth 客户端实现（`oauth2-pkce`、`react-oauth2-code-pkce` 等 provider-agnostic 零依赖库）后，本模块确立三条设计取向：

| # | 取向 | 依据 |
|---|------|------|
| 1 | **采用 OAuth 2.0 授权码流程 + PKCE**（RFC 6749 §4.1 + RFC 7636） | 这是浏览器/原生 App 场景的业界推荐流程，`state` 防 CSRF、PKCE 防授权码拦截 |
| 2 | **服务端主导，而非照搬纯 SPA 模式** | 上述开源库均为**纯前端**库，把流程放在浏览器。但 FeedFuse 已有服务端 session 体系，`client_secret`、`code → token` 交换、token 存储三个敏感环节**必须留在服务端**，浏览器只负责跳转与回跳，绝不接触 secret |
| 3 | **provider-agnostic 抽象层** | 四个平台能力不齐：GitHub 支持 PKCE；微信开放平台网站应用为传统授权码、**无 PKCE** 且 `redirect_uri` 需严格匹配（含 URL encode）；抖音/小红书是否支持 PKCE 待确认。因此抽象层必须支持「是否启用 PKCE」「平台特定 scope / redirect 规则」等差异化配置 |

**一句话**：做一个服务端主导的、provider-agnostic 的统一授权中心，前端只负责"点授权 → 跳走 → 跳回来 → 看状态"。

## 1. 项目信息

| 字段 | 值 |
|------|-----|
| 项目名 | `oauth-hub` |
| 所属产品 | FeedFuse |
| 技术栈 | Next.js + React + TypeScript + Tailwind CSS 4 + Radix UI + PostgreSQL（沿用现有栈，不引入新框架） |
| 覆盖平台 | GitHub、微信（开放平台网站应用）、抖音、小红书 —— **四家全做** |
| 原始需求 | 建设统一的三方授权中心：统一发起授权、处理平台回调、`state` 防 CSRF、PKCE（按需）、加密存储各平台 token、支持用户查看与撤销授权 |

### 1.1 范围边界（铁律）

| 类型 | 内容 |
|------|------|
| ✅ **本期做** | 授权发起、回调处理、token 加密存储、连接状态查看、撤销授权、平台应用（client_id/secret）配置管理 |
| ❌ **本期不做** | **各平台的数据抓取**。抖音/小红书/微信的数据 API 开放度极低，本期不碰。本模块只交付"拿到并管好授权凭证"这一层能力 |
| ⚠️ **不破坏性约束** | 现有 GitHub 模块使用「用户手动填 PAT」机制（`user_settings.github_token_encrypted` + 设置中心 `GitHub` 分区的"访问凭证"区块）。新授权中心走标准 OAuth 授权码流程，是**另一套独立机制**，两者**并存**，**不得改动或破坏现有 PAT 链路** |

> **关于 GitHub 双机制并存的产品说明**：现有 PAT 用于 GitHub 仓库 Release 抓取，属"数据访问凭证"；新 OAuth 连接属"身份授权凭证"，本期不承担抓取职责。二者用途不同、存储不同、入口不同（PAT 在「GitHub」分区，OAuth 在新增的「三方授权」分区），用户可只用其一或同时使用。

## 2. 产品定义

### 2.1 Product Goals

1. **统一入口** — 把四个平台碎片化的授权流程收敛到一个标准化、可复用的授权中心，用户在一个地方完成所有三方账号的连接与管理。
2. **安全可信** — 授权全链路符合 OAuth 2.0 安全实践：`state` 防 CSRF、PKCE 防码拦截、`client_secret` 与 token 永不出服务端、token 落库前加密；用户对自己的授权拥有完整的知情权与撤销权。
3. **可扩展底座** — 通过 provider 抽象层屏蔽平台差异，未来新增平台（或为已授权平台接入数据能力）只需扩展配置与适配器，不改动核心流程。

### 2.2 User Stories

| # | 用户故事 | 优先级 |
|---|---------|--------|
| US-1 | 作为**已登录用户**，我想在设置中心的「三方授权」分区一键授权 GitHub，跳转平台确认后自动跳回并显示"已连接"，以便后续功能使用该身份 | P0 |
| US-2 | 作为**已登录用户**，我想在一个列表中看到 GitHub / 微信 / 抖音 / 小红书四个平台各自的连接状态（已连接 / 未连接 / 已过期），以便一眼掌握自己的授权全貌 | P0 |
| US-3 | 作为**注重隐私的用户**，我想随时撤销某个平台的授权并确认本地存储的 token 已被清除，以便收回授权、控制风险 | P0 |
| US-4 | 作为**部署者/管理员**，我想在设置中填写各平台的 `client_id` / `client_secret`（secret 掩码显示），以便在自部署环境中启用对应平台的授权能力 | P0 |
| US-5 | 作为**已登录用户**，当授权失败时（用户取消、`state` 校验失败、平台未配置、平台返回错误），我想看到一句能看懂的中文错误提示而不是一堆报错码，以便知道下一步该怎么做 | P1 |
| US-6 | 作为**已连接用户**，我希望 access_token 过期时系统能用 refresh_token 自动续期，以便无需反复手动重新授权 | P1 |

## 3. 技术规范

### 3.1 需求池 (Requirements Pool)

#### P0 — Must Have（MVP 核心闭环）

| ID | 需求 | 描述 | 验收标准 |
|----|------|------|----------|
| R01 | **平台应用配置管理** | 在设置中提供全局（非用户级）的平台应用配置：每个平台可填 `client_id` / `client_secret`；secret 输入框掩码显示、回显时打码、明文永不返回前端；支持清除 | 四个平台各自可独立保存/清除；未配置的平台在卡片上显示"未配置"且授权按钮禁用；secret 回显为掩码（如 `••••1234`），接口响应中不含明文 |
| R02 | **授权发起** | 用户点击"授权"→ 服务端生成 `state`（防 CSRF）与 `code_verifier`/`code_challenge`（按平台是否支持 PKCE 决定）→ 拼装平台授权 URL → 浏览器跳转平台 | 点击后跳转到正确的平台授权页；URL 含 `client_id`、`redirect_uri`、`scope`、`state`；支持 PKCE 的平台额外含 `code_challenge` + `code_challenge_method` |
| R03 | **回调处理** | 平台回跳后：校验 `state`（不匹配/过期即拒绝）→ 用 `code`（+ `code_verifier`）向平台换取 token → 加密存储 → 跳回设置中心并提示结果 | `state` 校验失败时明确拒绝且不写入任何数据；成功后跳回「三方授权」分区并显示"已连接"；`state` 为一次性，重放无效 |
| R04 | **Token 加密存储** | 平台返回的 `access_token` / `refresh_token` / 过期时间等，加密后按用户维度存储 | token 明文不落库、不出网、不进日志；存储天然按 `userId` 隔离，用户 A 无法读到用户 B 的连接 |
| R05 | **连接列表** | 「三方授权」分区展示四张平台卡片，每张显示连接状态徽章（已连接 / 未连接 / 已过期 / 未配置）、授权时间、可用操作 | 四平台状态准确反映后端真实数据；页面加载有 loading 态；接口只返回状态与打码信息，不返回 token |
| R06 | **撤销连接** | 用户点击"撤销"→ 二次确认弹窗 → 删除该用户在该平台的授权记录与 token | 撤销后卡片立即变为"未连接"；本地 token 记录被清除；操作有成功/失败提示 |
| R07 | **用户可读的结果反馈** | 授权成功/失败、配置保存/清除、撤销成功/失败，均给出统一风格的中文提示 | 复用现有通知机制（`runImmediateSuccess` / `runImmediateFailure`），文案与设置中心其他模块一致 |

#### P1 — Should Have（增强体验）

| ID | 需求 | 描述 | 验收标准 |
|----|------|------|----------|
| R11 | **Token 自动刷新** | access_token 临近/已过期时，用 refresh_token 自动换取新 token；刷新失败则将状态置为"已过期"并提示重新授权 | 刷新成功对用户无感；刷新失败后卡片显示"已过期"+"重新授权"按钮 |
| R12 | **授权失败的细分错误提示** | 区分并友好呈现：用户取消授权、`state` 校验失败、平台未配置、`redirect_uri` 不匹配、平台返回业务错误码 | 每类失败有独立中文文案与建议动作；技术细节仅进日志，不糊到用户脸上 |
| R13 | **同一平台多账号** | 允许同一用户在同一平台连接多个账号（如两个 GitHub 账号） | 卡片可展开为账号列表；每个账号可独立撤销 |
| R14 | **重新授权（Re-auth）** | 已连接状态下允许重新走一次授权流程（用于换账号、扩 scope、修复过期） | 重新授权覆盖原记录而非产生脏数据 |

#### P2 — Nice to Have（远期）

| ID | 需求 | 描述 |
|----|------|------|
| R21 | **Provider 元信息展示** | 授权成功后拉取并展示平台侧用户 profile（头像 / 昵称 / 用户名），卡片上显示"已连接为 @xxx"，为将来"数据接入"预留元信息字段 |
| R22 | **撤销时级联清理** | 撤销授权时联动清理该连接衍生的数据（如未来接入数据后产生的缓存/同步内容），并在确认弹窗中告知影响范围 |
| R23 | **平台侧远程撤销** | 撤销时调用平台的 revoke 接口，同步在平台侧解除授权（而非仅删本地 token） |
| R24 | **授权审计日志** | 记录授权/撤销/刷新的时间线，供用户在界面上查看历史 |

### 3.2 UI 设计稿（文字描述）

#### 3.2.1 入口与信息架构

设置中心（`SettingsCenterDrawer`）左侧导航新增**一个独立分区**：

```
设置中心
├── 通用
├── RSS
├── AI
├── 账号与安全
├── Fever 账号
├── GitHub            ← 现有分区，内含"GitHub 仓库订阅" + "访问凭证(PAT)"，本期完全不动
├── 三方授权   ← 【新增】本模块唯一入口
└── 日志
```

> 新分区与现有 `GitHub` 分区**平级、并列、互不干扰**。GitHub 会同时出现在两处：`GitHub` 分区管的是 PAT 与仓库订阅，`三方授权` 分区管的是 OAuth 连接 —— 需通过文案明确区分，避免用户困惑（见 AQ-5）。

#### 3.2.2 「三方授权」分区页面结构

自上而下三个区块：

**① 顶部说明条**
一句话说明本分区用途与边界：*"连接你的三方账号用于身份授权。本功能仅获取并保管授权凭证，暂不抓取各平台数据。"*

**② 平台应用配置（可折叠区，默认折叠）**

| 元素 | 说明 |
|------|------|
| 区块标题 | 「平台应用配置」+ 副标题"自部署需先在各平台开放平台创建应用并填入凭据" |
| 折叠交互 | 默认折叠，展开后显示四个平台的配置组 |
| 每组字段 | 平台名 + `Client ID`（普通文本框）+ `Client Secret`（**掩码输入框**，已保存时回显 `••••1234` 形态）+ 「保存」「清除」按钮 |
| 状态提示 | 已配置显示绿色"已配置"小徽章；未配置显示灰色"未配置" |
| 只读提示 | 每个平台旁给出该平台的 `redirect_uri` 供用户复制到开放平台后台填写（微信需严格匹配，尤其重要） |

**③ 平台连接卡片列表（主体）**

四张卡片，纵向排列（窄屏单列 / 宽屏可两列）。每张卡片包含：

| 元素 | 说明 |
|------|------|
| 平台标识 | 平台图标 + 名称（GitHub / 微信 / 抖音 / 小红书） |
| 状态徽章 | `已连接`（绿）/ `未连接`（灰）/ `已过期`（琥珀）/ `未配置`（灰，禁用态） |
| 辅助信息 | 已连接时显示授权时间；P2 阶段追加"已连接为 @昵称"+头像 |
| 主操作按钮 | 未连接 → 「授权」；已连接 → 「重新授权」；已过期 → 「重新授权」（强调态）；未配置 → 按钮禁用 + tooltip"请先在上方配置该平台的 Client ID / Secret" |
| 次操作按钮 | 「撤销」（仅已连接/已过期时可见，destructive 语义） |
| 撤销确认 | 点击「撤销」弹出 `AlertDialog` 二次确认，文案说明"撤销后需重新授权才能再次使用" |

#### 3.2.3 视觉规范（强约束）

- **本期不做玻璃拟态 reskin**。视觉与既有设置中心保持**完全一致**。
- 只消费**语义 token**，不写死颜色：容器 `rounded-lg border border-border bg-background p-4`、标题 `text-sm font-medium text-foreground`、说明文字 `text-xs text-muted-foreground`、空/加载态 `border-dashed border-border/80 bg-muted/20`。
- 组件复用既有体系：`Button`（`size="compact"`）、`AlertDialog`（撤销确认）、折叠区沿用现有交互模式；反馈走 `runImmediateSuccess` / `runImmediateFailure`。
- 卡片结构对齐现有 `GithubSettingsPanel` 的 `<section>` 版式，保证同一抽屉内视觉节奏统一。

### 3.3 可复用底座（事实清单，供架构师参考，非架构设计）

| 能力 | 现有实现 | 说明 |
|------|---------|------|
| 用户身份 / session | `src/server/domains/auth/services/session.ts` → `requireApiSession()` | 可拿到当前 `userId`，OAuth 连接天然按用户隔离 |
| 对称加密 | `src/server/infra/crypto/secretBox.ts`（AES-256-GCM，`seal()`/`open()`，密文格式 `v1:iv:tag:ct`） | 直接用于 OAuth token 加密存储 |
| per-user 凭证存储范式 | `src/app/api/settings/github/token/route.ts` + `githubTokenService`（`getGithubTokenStatus` / `setGithubToken` / `clearGithubToken`，含 `maskToken`） | 新模块的"用户级连接"存储与"只返回打码状态"的接口风格应对标此模式 |
| 全局单例配置存储 | `app_settings` 单例表（参考 `0026_app_settings_auth.sql`、`0045_github_module.sql`） | 可扩展列用于存放各平台 `client_id` / `client_secret` |
| 统一响应与错误 | `src/server/infra/http/apiResponse`（`ok`/`fail`）、`ValidationError`（支持字段级错误） | 表单字段校验提示直接复用 |
| 前端反馈 | `runImmediateSuccess` / `runImmediateFailure`（`actionKey` 驱动） | 保持全站提示风格一致 |

## 4. 待确认问题 (Open Questions / AQ)

> 以下问题需**架构师**给出方案、必要时由**用户**拍板，是进入下一阶段前的阻塞项。

| # | 问题 | 影响 | 产品侧倾向 | 需谁拍板 |
|---|------|------|-----------|---------|
| **AQ-1** | **全局 `client_secret` 的存储方案**：① 明文存 `app_settings` 新增列 ② 用 `secretBox` 加密后存 `app_settings` ③ 建独立的平台配置表（支持多平台横向扩展） | 直接决定安全等级与后续扩展平台的成本 | 倾向 **②+③ 组合**：独立配置表（一平台一行，扩展新平台无需 DDL）+ secret 经 `secretBox` 加密。理由：`app_settings` 是单例宽表，四个平台各加两列会迅速膨胀；且 secret 属最高敏感级，不应明文落库 | 架构师 |
| **AQ-2** | **PKCE `code_verifier` 的临时存放位置**：① 服务端临时表（带 TTL，与 `state` 同生命周期）② 服务端 session ③ 加密 cookie | 决定授权流程的可靠性（多标签页、跨设备回调）与清理机制 | 倾向 **①**：`state` 与 `code_verifier` 天然同生命周期（一次性、短 TTL、用后即删），存同一张临时表最自然，且不受 session 体积与多标签页竞态影响。需明确 TTL（建议 10 分钟）与过期清理策略 | 架构师 |
| **AQ-3** | **微信/抖音/小红书需企业资质审核才能拿到 `client_id`/`secret`，本机无法端到端验证**。这三家的交付标准如何界定与标注？ | 决定验收口径与"完成"的定义，避免工程师交付无法验证的代码被误判为完成 | 倾向：**四家均完整实现 provider 适配器与流程代码**；验收时 **GitHub 必须端到端跑通**（真实授权→回调→存储→撤销），其余三家标注为「**待配置 client 后验证**」，以**契约测试/mock 平台响应**覆盖，并在 UI 上对未配置平台显示"未配置"引导态。**此口径需用户确认** | 用户 + 架构师 |
| **AQ-4** | **抖音 / 小红书是否支持 PKCE？**（GitHub 支持；微信明确不支持） | 决定 provider 抽象层的字段设计（`supportsPkce` 是否够用、是否还需 `codeChallengeMethod` 等） | 需架构师查阅两家最新开放平台文档确认。产品侧要求：**抽象层必须以"能力开关"方式建模**，即便结论待定也不阻塞开发——先按"不支持 PKCE"保守实现，确认支持后开开关即可 | 架构师 |
| **AQ-5** | **GitHub 在设置中心出现两处（`GitHub` 分区的 PAT / `三方授权` 分区的 OAuth），如何避免用户困惑？** | 影响用户认知成本与支持成本 | 倾向：两处均加一句互指说明——PAT 处注明"用于仓库 Release 抓取"，OAuth 处注明"用于账号身份授权，不影响仓库订阅"。**文案需最终确认** | 用户 |
| **AQ-6** | **`redirect_uri` 的来源**：从环境变量/站点配置读取，还是让用户在配置区手填？ | 微信要求 `redirect_uri` 严格匹配（含 URL encode），自部署用户域名各异，配错是最高频故障点 | 倾向：**由服务端根据站点配置自动推导并在 UI 上只读展示 + 一键复制**，让用户去平台后台粘贴，而非手填，减少出错面 | 架构师 |
